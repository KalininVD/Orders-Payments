# API для Заказов и Платежей

## Обзор проекта

Этот проект представляет собой реализацию распределенной бэкенд-системы, состоящей из двух ключевых микросервисов: **Сервис Платежей (Payments Service)** и **Сервис Заказов (Orders Service)**. Система спроектирована для надежной и масштабируемой обработки процессов создания и оплаты заказов клиентов.

-   **Сервис Платежей:** Отвечает за управление счетами пользователей, их балансами и обработку пополнений.
-   **Сервис Заказов:** Отвечает за управление жизненным циклом заказов, от создания до завершения или отмены.

Всё взаимодействие с внешним миром происходит через выделенный **API-шлюз (API Gateway)**, который служит единой точкой входа в систему. Проект предполагает, что существует внешний сервис для управления пользователями, и `user_id` передается в качестве известного параметра.

## Поддерживаемые эндпоинты API

Все API доступны через API Gateway.

### Payments Service (`/api/accounts`)

-   `POST /api/accounts`: Создать новый счет для пользователя с нулевым балансом
-   `POST /api/accounts/deposit`: Пополнить счет пользователя
-   `GET /api/accounts/{id}`: Получить информацию о счете по его уникальному ID
-   `GET /api/accounts`: Получить информацию о счете по ID пользователя

### Orders Service (`/api/orders`)

-   `POST /api/orders`: Создать новый заказ - асинхронно запускает процесс автооплаты
-   `GET /api/orders`: Получить список всех заказов для конкретного пользователя
-   `GET /api/orders/{id}`: Получить детали и текущий статус конкретного заказа
-   `PATCH /api/orders/{id}/cancel`: Отменить заказ по его ID

## Асинхронное взаимодействие

Основной бизнес-процесс создания и оплаты заказа полностью асинхронен:

1.  Клиент отправляет `POST` запрос в `Orders Service` для создания заказа. Заказ немедленно создается со статусом `NEW`.
2.  `Orders Service` атомарно сохраняет новый заказ в своей базе данных и публикует сообщение `OrderPaymentRequest` в брокер сообщений **RabbitMQ**.
3.  `Payments Service` получает это сообщение, находит счет пользователя и пытается списать необходимую сумму.
4.  В зависимости от результата, `Payments Service` публикует соответствующее событие: `OrderPaymentSucceeded` (оплата успешна) или `OrderPaymentFailed` (оплата не удалась).
5.  `Orders Service` получает ответное событие и обновляет статус заказа на `FINISHED` или `CANCELLED`, таким образом завершая жизненный цикл заказа.

## Локальный запуск

### Требования

-   Установленные Docker и Docker Compose (рекомендуется Docker Desktop).
-   Файл `.env` для конфигурации.

### Инструкция

1.  Склонируйте репозиторий.
2.  Создайте файл `.env` в корневой директории, скопировав содержимое из `.env.example`. При необходимости измените значения.
3.  Выполните следующую команду в корневой директории проекта:
    ```bash
    docker-compose up --build -d
    ```
4.  Дождитесь запуска всех контейнеров. Система готова к работе.
5.  Для взаимодействия с API откройте единый Swagger UI, размещенный на API-шлюзе: **`http://localhost:8080/swagger`** (используйте порт, указанный в `.env`).
6.  В качестве альтернативы вы можете использовать `.http` файлы в проектах `Web` каждого сервиса или в проекте `APIGateway` для отправки запросов напрямую из вашей IDE (например, VS Code с расширением REST Client или JetBrains Rider).

## Архитектура и паттерны проектирования

### Высокоуровневая архитектура

-   **Микросервисная архитектура:** Система разделена на независимые, развертываемые по-отдельности сервисы (`OrdersService`, `PaymentsService`) с единой точкой входа через **API-шлюз** (реализован с помощью YARP).
-   **Database-per-Service:** Каждый микросервис имеет собственную изолированную базу данных PostgreSQL, что обеспечивает независимое управление данными сервисов.

### Дизайн приложения

-   **Чистая архитектура (Clean Architecture):** Каждый сервис следует строгому разделению ответственностей с зависимостями, направленными внутрь. Это изолирует бизнес-логику от внешних фреймворков и технологий.
    -   **Доменный слой (Domain Layer):** Содержит "богатые" доменные сущности (`Order`, `Account`), которые инкапсулируют бизнес-правила и защищают собственное состояние (инварианты). Это следует принципу **DDD**.
    -   **Слой приложения (Application Layer):** Оркестрирует сценарии использования (use cases) приложения. Построен на основе паттерна **CQRS (Command Query Responsibility Segregation)** с использованием **MediatR** для разделения команд (операций, изменяющих состояние) и запросов (операций чтения данных).
    -   **Слой инфраструктуры (Infrastructure Layer):** Содержит реализации внешних зависимостей, таких как доступ к базе данных (**паттерн "Репозиторий"** и **"Единица работы" (Unit Of Work)** с Entity Framework Core) и интеграция с брокером сообщений.
    -   **Слой Web API:** Точка входа для внешних запросов, содержащая контроллеры, которые вызывают слой приложения для обработки запросов и возвращают RESTful ответы в формате JSON.

### Паттерны надежности и обмен сообщениями

Для обеспечения консистентности данных и надежного взаимодействия в распределенной среде используются паттерны обмена сообщениями, реализованные с помощью **MassTransit** и **RabbitMQ**.

-   **Паттерн Saga (на основе хореографии):** Весь процесс обработки заказа реализован как Saga. Центральный оркестратор отсутствует; вместо этого сервисы взаимодействуют, публикуя события и подписываясь на них. `OrdersService` инициирует Saga, публикуя запрос на оплату, а `PaymentsService` продолжает её, публикуя результат платежа. Это гарантирует, что вся бизнес-транзакция либо завершится успешно, либо будет корректно отменена.
-   **Transactional Outbox:** Этот паттерн гарантирует, что сообщение будет отправлено в брокер **тогда и только тогда, когда** соответствующая транзакция в базе данных будет успешно зафиксирована. При создании заказа сущность `Order` и сообщение `OrderPaymentRequest` сохраняются атомарно. Это предотвращает сценарии, когда заказ сохранен, но запрос на оплату так и не был отправлен.
-   **Transactional Inbox (Идемпотентные потребители):** Этот паттерн обеспечивает обработку входящих сообщений **ровно один раз**. MassTransit использует таблицу `InboxState` для отслеживания уже обработанных сообщений. Если сообщение будет доставлено повторно (например, из-за сбоя сети), потребитель обработает его только в первый раз, предотвращая дублирующиеся операции, такие как двойное списание средств с клиента.
-   **Семантика Exactly-Once для списаний денег со счета пользователя:**
    - В сущности `Account` включена оптимистичная блокировка через столбец `RowVersion` (`Version` типа `byte[]`), настроенный в _EF Core_.
    - В `OrderPaymentRequestConsumer` выполняется загрузка аккаунта, вызывается `Withdraw(amount)`, затем `SaveChangesAsync()`.
    - Исключение `DbUpdateConcurrencyException` приводит к повторной попытке (до $3$ раз с небольшой задержкой между попытками).
    - Событие `OrderPaymentSucceeded` публикуется только после успешного коммита транзакции.
    Такой подход гарантирует, что каждое списание будет выполнено **ровно один раз** на уровне базы данных - даже при высокой конкуренции - и исключает публикацию события об успехе, если средства фактически не были списаны.

### Другие реализованные паттерны

-   **Options Pattern:** Для строгой типизации, безопасности и валидации конфигурации приложения.
-   **Пользовательский Middleware:** Для централизованной и единообразной обработки исключений в API.
-   **Внедрение зависимостей (Dependency Injection):** Широко используется во всем приложении для достижения слабой связанности и высокой тестируемости.

## Качество кода и Тестирование

-   **Модульное тестирование (Unit-тесты):** Основная бизнес-логика, расположенная в слоях `Domain` и `Application`, полностью покрыта модульными тестами. Это гарантирует, что все бизнес-правила, сценарии использования и ветвления логики проверены изолированно.
    -   **Используемые фреймворки:** xUnit, Moq и FluentAssertions.
    -   **Покрытие кода:** Проект достигает **покрытия строк кода (line coverage) на уровне 82%**.

-   **Ручное сквозное тестирование (End-to-End):** Предоставленные `.http` файлы позволяют проводить полное сквозное тестирование всей системы, проверяя корректность асинхронного взаимодействия между всеми сервисами через API-шлюз.
